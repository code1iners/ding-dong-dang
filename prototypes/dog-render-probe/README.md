# 강아지 그리는 방식 실험 (07번, 버리는 코드)

초당 60번으로 올린 강아지의 CPU(22%)를 줄일 수 있는지 보려고 그리는 방식 둘을 한 테마(기본 테마)로 만들어 지금 방식과 비교했다. 제품 코드에는 합치지 않았다. 결과로 **지금 방식(초당 60번)을 그대로 두기로** 했다(2026-11-20 사용자 결정).

## 파일

- `probe.ts`: 두 방식. 평소(idle) · 이동(move) 동작만 대신한다.
  - `sprite`: 동작 한 바퀴(4초)를 초당 60장 PNG 프레임으로 구워 한 장짜리 묶음으로 만들고 CSS `steps()` 둘(가로 · 세로 translate)로 넘긴다.
  - `waapi`: 한 바퀴를 초당 30번 뽑은 키프레임을 요소마다 Web Animations API(transform)로 넘긴다.
- `hook.patch`: `DogArt.tsx` · `dog-window.ts`에 방식을 끼우고, 강아지 창 CSP에 `img-src data: blob:`을 여는 임시 패치. `build-variants.sh`가 적용했다가 되돌린다.
- `build-variants.sh`: 패치를 적용한 채 `base` · `sprite` · `waapi` 세 가지로 빌드해 `/tmp/dog-probe/<방식>/`에 둔다.
- `measure.mjs`: 앱 프로세스 트리 전체의 누적 CPU 시간 차이로 코어 하나 기준 %를 낸다(28번과 같은 방법, 예열 30초 뒤). `ring`(고리 안만) · `roam`(`--auto-start`로 앱 창 없이 돌아다니는 창만) · `both`.
- `run-all.sh`: 세 방식 × 세 구성을 차례로 잰다(둘 다 600초, 나머지 300초). 결과는 `results.jsonl`.
- `class-all-day.json`: 하루 종일 수업 시간인 시간표를 넣은 저장 값(`measure.mjs`가 `/tmp/t07-data.json`으로 읽는다).

## 읽는 법

- 비용 대부분이 GPU · 렌더러의 합성이다. 메인 프로세스는 3% 안팎이다. 그래서 비용은 그리는 방식보다 **그리는 횟수(화면을 새로 합성하는 횟수)**에 달려 있다.
- sprite는 고리 안에서만 조금 낮고(21 → 16), 돌아다니는 창에서는 오히려 높고(13 → 17), 둘 다 켜면 같다(20). 큰 투명 묶음 이미지를 매 프레임 옮겨 그리는 비용이 JS 행렬 계산을 줄인 이득을 상쇄한 것으로 본다(추정). 묶음 PNG는 고리 안 2.3MB(6990×7456), 돌아다니는 창 동작당 1.2~1.6MB였다.
- waapi는 SVG 요소마다 애니메이션이 걸려 SVG가 프레임마다 다시 래스터라이즈되고 컴포지터 가속도 받지 못해 4배 이상 나쁘다.
- 한계: 한 번씩만 쟀고 부하 평균이 흔들렸다(8~40). 세 방식 사이 몇 %p 차이는 오차 안일 수 있다. 화면 품질(테두리 · 부드러움)은 눈으로 보지 않았다. 한 바퀴 4초의 끝에서 일부 부위가 튈 수 있다.
