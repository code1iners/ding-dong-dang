# 앱 내 업데이트는 최상위 번들의 명시 요구 조건과 앱의 Ed25519 검증에 기댄다

딩동댕은 코드 서명과 공증 없이 배포한다. macOS는 ad-hoc 서명, Windows는 서명 없음이다. 그런데 사용자는 설정 화면에서 업데이트하고 다시 실행하는 기능을 두 OS 모두에서 원한다. electron-updater의 macOS 설치기(Squirrel.Mac)는 설치된 앱의 지정 요구 조건으로 새 번들을 검증하는데, 기본 ad-hoc 서명의 요구 조건은 빌드마다 바뀌는 cdhash라서 그대로면 모든 업데이트가 거부된다.

그래서 electron-builder가 번들을 ad-hoc 서명한 뒤, 최상위 앱 번들만 `designated => identifier "<앱 식별자>"`로 다시 서명한다. `mac.requirements`로 넣으면 중첩 코드까지 같은 조건이 붙어 서명이 깨지므로 쓰지 않는다. 같은 방식을 쓰는 `~/workspace/work/stardraft`가 2026-10-19에 macOS 27에서 업데이트와 재실행을 실기로 확인했다(그 저장소의 `docs/adr/0002-in-app-update-trust.md`). 딩동댕의 Electron 버전에서는 구현 뒤에 확인한다.

이 조건은 신원을 보장하지 않고, Windows는 서명을 아예 보지 않는다. 앱 내 업데이트는 Gatekeeper와 SmartScreen을 거치지 않으므로, 릴리스를 만들 수 있는 GitHub 계정이 털리면 가짜 버전이 설치된 모든 PC에 퍼진다. 그래서 업데이트 안내 파일(`latest*.yml`)에 Ed25519 서명을 넣고, 앱에 넣은 공개 키로 검증한 파일만 설치 후보로 삼는다.

## Considered Options

- **macOS는 dmg를 내려받아 열어 주기만 한다**: 서명 조건에 기대지 않지만 사용자가 끌어다 놓고 다시 열어야 한다. 사용자가 두 OS를 같게 해 달라고 해서 고르지 않았다.
- **sha512 무결성 확인만 한다**: 키 관리가 없지만 계정이 털린 경우를 막지 못한다.

## Consequences

- 명시 요구 조건이 빠진 버전이 한 번 나가면, 그 버전을 설치한 Mac은 이후 업데이트가 조용히 모두 거부된다. 다시 설치해야 풀린다. 그래서 릴리스 명령이 올리기 전에 요구 조건을 검사하고, 틀리면 올리지 않는다.
- 개인 키를 잃으면 새 키를 넣은 버전을 모든 PC에 수동으로 설치해야 한다. 개인 키는 개발 Mac의 Keychain과 `/Users/wraith/workspace/keys/ding-dong-dang`에 두고 저장소에는 넣지 않는다. 안내 파일의 서명 필드는 처음부터 목록으로 두어 키를 바꾸는 동안 두 키로 함께 서명할 수 있게 한다.
