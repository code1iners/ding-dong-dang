# 돌아다니는 강아지 창을 Mac에서 검증하기

Type: task
Status: resolved
Blocked by: 

## Question

[강아지 연출의 범위와 동작 결정](09-roaming-dog-behavior.md)에서 정한 돌아다니는 강아지가 Electron 창으로 실제로 되는가? 버리는 최소 앱을 만들어 에이전트가 Mac에서 재고 관찰을 기록한다. 배경은 [화면 바닥을 돌아다니는 강아지 연출의 구현 가능성 조사](04-roaming-dog-feasibility.md)의 미확인 항목이다.

- 창의 형태를 정한다: 강아지 크기의 작은 창을 움직이는 방식과 화면 전체를 덮는 투명 · 클릭 통과 창 방식을 둘 다 만들어 비교한다. 끌기, 낙하산과 하트가 강아지 밖으로 나가는 것, 화면 나머지가 평소처럼 눌리는 것을 모두 만족해야 한다.
- 창이 뜨거나 강아지를 눌러도 작업 중인 다른 앱의 포커스를 뺏지 않는지.
- 다른 창 위와 Dock 바로 위에 항상 보이는지, 전체 화면 앱 위에서는 어떻게 되는지.
- 강아지를 끄는 동안 커서를 놓치지 않고 따라오는지, 주 모니터 밖으로 나가지 않는지.
- 수업 시간의 행동(걷기 5~10초, 쉬기 10~20초)을 10분 넘게 돌렸을 때의 평균 CPU 사용량. 한 코어의 5%를 넘으면 프레임 수나 걷는 비율을 줄여 다시 잰다.
- 화면 잠금 · 화면 꺼짐을 `powerMonitor`로 알아 애니메이션을 멈출 수 있는지(에이전트가 할 수 있는 범위까지).
- 종이 울리는 동안에만 나타나는 경우(설정 끔)도 같은 창으로 되는지.

Windows에서의 확인은 하지 않는다. `checklists/post-implementation.md`에 넘겨 두었다.

## Answer

돌아다니는 강아지는 Electron 창으로 된다. 창은 **강아지보다 조금 큰 투명 창 하나를 움직이는 방식**으로 만든다. 2026-11-17에 버리는 측정용 앱 `prototypes/dog-window-probe/`를 만들어 에이전트가 Mac에서 쟀고, 아래 "사용자 결정" 셋은 사용자가 결과를 보고 정했다.

측정 조건: MacBook Pro(M5 Pro, 18코어), macOS 27.2.1, Electron 45.3.3, 주 모니터 1512×982(2배율, 120Hz), Dock 자동 숨김, 모니터 3대. 강아지는 [돌아다니는 강아지 시안](../assets/09-roaming-dog.html)의 뻐드렁니 강아지와 부위 움직임 코드를 그대로 썼고 키는 96이다. 클릭과 끌기는 `cliclick`으로 실제 마우스 입력을 합성했다.

### 사용자 결정

- **창 방식은 작은 창 이동이다.** 두 방식 모두 아래 확인을 통과했다. Windows에서 투명 배경이 검게 나오는 문제가 생기면 작은 창은 강아지 주변 네모만 검어지고 화면 전체 창은 모니터 전체가 검어지므로 작은 창을 골랐다. CPU는 작은 창이 한 코어의 0.6~0.9% 더 쓴다.
- **Mac에서 강아지를 누르면 딩동댕이 맨 앞 앱이 되는 것은 감수한다.** 손을 뗀 뒤 앱을 숨겼다 다시 보여 원래 앱으로 돌려주는 대책은 넣지 않는다.
- **프레임 수는 걷기 24, 멈춤 4다.** 걸을 때(통통 튀기 · 신남 · 끌려가기 · 낙하 포함) 초당 24번, 멈춰 쉴 때(평소 · 졸림) 초당 4번 그린다.

### 창 만드는 법 (확인된 구성)

- 창 옵션: 틀 없음, 투명, 그림자 없음, 크기 고정, `focusable: false`, `type: 'panel'`, `alwaysOnTop` 레벨 `pop-up-menu`, `setVisibleOnAllWorkspaces(true, { visibleOnFullScreen: true, skipTransformProcessType: true })`. 보일 때는 `showInactive()`를 쓴다.
- 창 크기: 낙하산 · 하트 · 끌 때의 흔들림이 들어가도록 너비 `max(1.6W + 92, W + 0.75H, 1.5H) + 8`, 높이 `1.925H + 18`(W · H는 강아지의 너비 · 키). 키 96인 뻐드렁니 강아지에서 281×203이고, 캡처에서 하트와 낙하산이 창 안에 다 들어왔다. 강아지는 창의 아래쪽 가운데에 고정하고 창을 `setBounds`로 옮긴다.
- 클릭 통과: 평소에는 `setIgnoreMouseEvents(true)`로 두고, 메인 프로세스가 33ms마다 커서 위치를 읽어 강아지 네모 안이면 `false`로 바꾼다. `forward: true` 옵션은 쓰지 않았다(Windows의 커서 깜빡임 이슈 electron#35414를 피한다). 누르는 중과 끄는 중에는 `false`로 유지한다.
- 끌기: 렌더러는 누름과 뗌만 받고, 끄는 동안의 위치는 메인의 `screen.getCursorScreenPoint()`로 계산한다. 창이 움직이는 동안 포인터 이벤트의 화면 좌표를 쓰지 않는다.
- 바닥은 주 모니터 `workArea`의 아래쪽, 좌우 · 위 한계는 주 모니터 `bounds`다.

### 확인된 것

| 항목 | 작은 창 | 화면 전체 창 |
| --- | --- | --- |
| 강아지를 누르면 하트(창 안에 다 보임) | 됨 | 됨 |
| 강아지 밖의 클릭이 밑의 창에 전달됨 | 구조상 창 밖이라 해당 없음(창 안 투명 영역은 미확인) | 됨(과녁 창이 클릭을 받음) |
| 끄는 동안 커서를 따라옴 | 됨(놓은 위치가 커서 위치와 일치) | 됨 |
| 주 모니터 밖으로 나가지 않음 | 됨(위 모니터로 커서를 올려도 강아지는 맨 위에서 멈춤, 좌 · 우 끝에서 멈춤) | 됨(위 · 왼쪽 확인, 오른쪽은 합성 입력이 먹지 않아 미확인) |
| 놓으면 낙하산으로 내려와 착지 | 됨 | 됨 |
| 창이 뜰 때 포커스를 뺏지 않음 | 됨 | 됨 |
| 다른 앱 창 위에 보임 | 됨 | 됨 |
| 전체 화면 앱 위에 보임 | 됨 | 됨(`type: 'panel'`일 때만. 빼면 안 보임) |
| 설정 끔 상태에서 종이 울릴 때만 나타났다 사라짐 | 됨(포커스 안 뺏음) | 됨 |

- **포커스**: 창이 뜨거나 종 때문에 나타날 때는 맨 앞 앱이 바뀌지 않는다. 강아지를 누르면 창 방식 · `panel` 여부 · Dock 아이콘 유무를 바꾼 여섯 조합 모두에서 앱이 활성화됐다(`did-become-active`, 맨 앞 앱이 Electron으로 바뀜). 창 자체는 포커스를 받지 않는다. 손을 뗀 뒤 `app.hide()`를 부르면 맨 앞 앱이 원래대로 돌아가지만 강아지 창도 숨는다. 바로 다시 보이면 안 보이고(지연 0ms 실패), 500ms 뒤 `showInactive()`를 부르면 포커스를 유지한 채 다시 보였다. 그 사이의 지연은 재지 않았다.
- **Dock**: 레벨 `floating`에서는 강아지가 Dock 뒤에 가려지고 `pop-up-menu`에서는 Dock 위에 그려진다. 측정한 Mac은 Dock 자동 숨김이라 `workArea` 바닥이 화면 맨 아래이고, Dock이 올라오면 강아지가 Dock 아이콘 위에 겹친다. Dock이 항상 보이는 Mac에서 Dock 바로 위에 서는지는 재지 않았다(`workArea`가 Dock을 뺀 값을 준다는 문서에 따른다).
- **작은 창의 화면 밖 부분**: 강아지가 가장자리에 있으면 창의 여백이 주 모니터 밖으로 나간다(창 좌표 x −84, y −101까지 확인). macOS가 창을 밀어내지 않았다.
- **화면 잠금**: `powerMonitor`에 `lock-screen` · `unlock-screen` · `suspend` · `resume` 이벤트가 있고, 화면만 꺼지는 것을 알리는 이벤트는 없다. 이 이벤트에 그리기 정지를 걸어 두었고, 정지 경로를 손으로 불러 그리기 횟수가 0이 되고 CPU가 한 코어의 0.7~1.1%로 떨어지는 것을 확인했다. 실제로 화면을 잠그거나 끄지는 않았다.

### CPU (한 코어 기준, 앱의 모든 프로세스 합)

`app.getAppMetrics()`의 `percentCPUUsage`는 코어 수로 나눈 값이라 쓰지 않고, 프로세스별 누적 CPU 시간의 차이로 계산했다(`ps`와 맞춰 봤다). 수업 시간 행동(걷기 5~10초, 멈춰 쉬기 10~20초)을 실제 간격으로 10분 30초씩 돌렸고 걷는 시간은 전체의 31~36%였다.

| 그리는 횟수(걷기 / 멈춤) | 작은 창 | 화면 전체 창 |
| --- | --- | --- |
| 120 / 120 (화면 주사율 그대로, 1분 예비 측정, 걷는 비율 60%) | 25% | 21% |
| 60 / 60 (1분 예비 측정) | 16.6% | 13.3% |
| 30 / 30 (1분 예비 측정) | 11.2% | 9.2% |
| 30 / 10 | 5.9% | 5.0% |
| 30 / 5 | 5.3% | 재지 않음 |
| 24 / 8 | 5.1% | 4.3% |
| **24 / 4** | **4.2%** | 3.6% |
| 30 / 멈춤 고정 | 4.3% | 3.2% |
| 24 / 멈춤 고정 | 3.5% | 재지 않음 |
| 쉬는 시간(졸림) 10 | 재지 않음 | 4.1% |
| 정지(화면 잠금 경로) | 0.7% | 1.1% |

- 비용은 그리는 횟수에 거의 비례하고, 멈춰서 숨만 쉬는 동작도 걷기와 같은 만큼 든다. 부위마다 SVG `transform`을 다시 써서 그림 전체를 다시 그리기 때문이다. 화면 주사율에 맞춘 `requestAnimationFrame`을 그대로 쓰면 안 되고 타이머로 횟수를 정해야 한다.
- 걷지 않는 동안의 바닥값은 0.7~1.1%이고 대부분 메인 프로세스의 33ms 커서 확인이다.
- 측정은 여러 조건(4~6개)을 한꺼번에 띄워서 했다. 서로 영향을 주었을 수 있다.
- 걷기 24 · 멈춤 4에서 움직임이 눈에 어떻게 보이는지는 사용자가 보지 않았다. 구현 뒤 수동 통합 테스트에서 본다.

### 확인하지 못한 것

- 내려오는 중에 다시 잡기: 합성 입력이 커서 확인 주기(33ms)보다 빨리 눌러 클릭이 통과했다. 사람 손으로는 구현 뒤에 확인한다. 같은 이유로, 커서가 강아지 위에 올라온 뒤 33ms 안에 누르면 클릭이 밑으로 통과한다.
- 작은 창 안의 투명한 여백을 눌렀을 때 밑의 창이 눌리는지(강아지 네모 밖은 `setIgnoreMouseEvents(true)` 상태라 통과해야 한다).
- 실제 화면 잠금 · 화면 꺼짐 때 이벤트가 오는지, 그동안 CPU가 떨어지는지.
- Dock이 항상 보이는 Mac, 통통 튀는 테마, 키 160에서의 CPU, 배터리로 쓸 때.
- Windows 전체. 위 항목과 함께 [구현 뒤 확인 목록](../checklists/post-implementation.md)에 넘겼다.

### 측정용 앱

`prototypes/dog-window-probe/`(버리는 코드). `python3 build-renderer.py`로 시안에서 `dog.html`을 만들고 `../bell-probe/node_modules/.bin/electron . --mode=small|overlay`로 띄운다. `input-test.sh`(누르기 · 끌기 · Dock · 전체 화면), `refocus-test.sh`(포커스 돌려주기), `run-cpu.sh`와 `summarize.py`(CPU)가 있다. 로그와 캡처는 다른 앱 화면이 찍혀 있어 커밋하지 않았다.
