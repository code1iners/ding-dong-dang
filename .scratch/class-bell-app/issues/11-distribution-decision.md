# 배포와 설치 방식 결정

Type: grilling
Status: resolved
Blocked by: 02, 14

## Question

학원 PC에 앱을 어떤 형식으로 전달하고 설치하게 하는가?

- Windows와 macOS 각각의 설치 파일 형식.
- 서명 경고를 넘기는 안내문의 형태와 전달 방법.
- Smart App Control 대응 UI(사용자 요청): Smart App Control이 켜진 PC에서는 앱과 설치 파일이 실행 전에 차단되므로 앱 안의 화면으로는 안내할 수 없다. 대응 UI를 어디에 둘지(설치 전 안내 페이지 · 문서, 설치 프로그램 화면, 설치 뒤 앱 안의 도움말)와 무엇을 안내할지(상태 확인 방법, 끄는 절차와 그 영향)를 정한다. 화면 모양은 시안으로 보여 주고 고른다.
- 학원 PC의 Smart App Control 상태는 확인하지 않았다. 켜져 있을 수 있다고 가정하고 정한다([학원 PC의 Smart App Control 상태 확인](13-academy-pc-sac-check.md)).
- 빌드를 어디서 하는지(개발 PC, CI).
- 새 버전을 전달하는 방법(자동 업데이트는 범위 밖).

## Answer

2026-11-17에 사용자와 그릴링으로 정했다. 근거는 [서명 없는 앱의 앱 내 업데이트 가능성 조사](25-unsigned-in-app-update.md), [내려받기 페이지 레퍼런스와 제공 경로 조사](26-download-page-references.md), [서명 없는 빌드 산출물의 설치 실측](14-unsigned-build-install-measurement.md), 그리고 같은 방식을 이미 쓰는 `~/workspace/work/stardraft`의 결정과 실기 확인이다.

### 설치 형식

- Windows: electron-builder의 NSIS 설치 파일 하나. 원클릭, 사용자별 설치(관리자 권한 불필요). 바탕 화면과 시작 메뉴에 바로가기를 만들고 설치가 끝나면 앱을 띄운다.
- macOS: Apple Silicon 전용 dmg, ad-hoc 서명. Intel Mac은 지원하지 않는다. 앱 내 업데이트용 zip도 함께 만든다.

### 빌드와 릴리스

- 개발 Mac에서 명령 하나로 빌드, 자동 검사, GitHub Releases 게시까지 한다. Windows 설치 파일은 베타 NSIS 툴셋(`toolsets.nsis: "1.2.1"`)으로 만든다.
- 올리기 전 자동 검사: Mac 최상위 번들의 지정 요구 조건, 버전 없는 파일 이름, 업데이트 안내 파일(`latest.yml`, `latest-mac.yml`)과 그 서명. 하나라도 틀리면 올리지 않는다.
- 릴리스는 초안이 아닌 게시 상태로 올린다. 태그는 semver다.
- 대비책: 이 Mac에서 만든 Windows 설치 파일이 구현 뒤 수동 테스트에서 제대로 설치되지 않으면 GitHub Actions의 Windows 러너로 옮긴다.
- 잘못 나간 버전은 그 릴리스를 사전 릴리스로 바꿔 멈춘다. 이미 업데이트한 PC를 되돌리는 기능은 두지 않고 고친 새 버전을 올린다.

### 저장소와 내려받기 주소

- 공개 GitHub 저장소 하나에 소스와 릴리스를 함께 둔다. 배포 전용 저장소를 따로 두지 않는다.
- 설치 파일 이름에 버전과 공백을 넣지 않아(`artifactName` 지정) `releases/latest/download/<파일 이름>` 고정 주소를 쓴다.

### 내려받는 곳 (학원 사이트)

- 학원 사이트(`https://pet-grooming-cdh.squadify.app/`, 저장소 `~/workspace/personal/pet-grooming-cdh`) 첫 페이지에 "앱 다운로드" 영역을 새로 만들고 상단 메뉴에도 넣는다. "자료실"은 문서 게시판에 남은 이름이라 쓰지 않는다(한국어 사이트 27곳의 메뉴를 조사했고, 앱을 내려받는 자리는 거의 전부 "다운로드" 또는 "앱 다운로드"였다).
- 영역 안에 앱마다 카드 하나를 둔다. 카드에는 아이콘, 이름, 한 줄 소개, OS별 다운로드 버튼 두 개, "설치 방법" 링크가 있다. 앱이 늘면 카드를 더한다.
- 다운로드 버튼은 글자 없이 OS 아이콘만 둔다(Windows, Mac). 아이콘만 있는 버튼이라 화면 읽기 프로그램용 이름은 따로 붙인다.
- 버튼은 GitHub Releases의 고정 주소를 가리키는 평범한 링크다. 누르면 페이지는 그대로 있고 내려받기가 바로 시작된다(GitHub가 첨부 파일로 응답한다. 추가 개발은 필요 없다).
- "설치 방법"은 GitHub README로 간다. 별도의 내려받기 페이지는 만들지 않는다.
- 영역의 화면 시안과 제작은 학원 사이트 저장소의 별도 작업이다. 이 앱의 스펙에는 카드가 가리킬 고정 주소와 README 주소만 적는다.

### 설치 안내 (README와 영상)

- 설치 안내는 설치 전에 볼 수 있는 곳에 있어야 한다(Smart App Control이 켜진 PC에서는 설치 파일이 실행 전에 차단된다). 앱 안과 설치 프로그램 화면에는 안내를 두지 않는다.
- 공개 저장소의 README를 한국어로 쓴다. 순서는 소개 영상, 한 줄 소개, 내려받기 링크(Windows · Mac), Windows 설치 영상과 글 절차, Mac 설치 영상과 글 절차, 업데이트 방법이다. 개발자용 내용은 맨 아래나 별도 문서로 내린다.
- Windows 글 절차: 설치 파일 실행, SmartScreen 통과가 본편이다. "차단 화면이 뜨면"으로 시작하는 Smart App Control 부분을 뒤에 두고 상태 확인 방법, 끄는 절차, 끄면 생기는 영향(서명 없는 다른 앱도 실행 가능해지고, Windows 버전에 따라 다시 켜려면 초기화가 필요할 수 있음)을 모두 적는다.
- Mac 글 절차: 열기 시도 뒤 시스템 설정 > 개인정보 보호 및 보안의 "그래도 열기".
- 영상은 셋이다. 소개 영상 하나(30초 안쪽: 시간표 등록, 종이 울릴 때 뜨는 강아지, 강아지 테마)와 설치 안내 영상 OS별 하나씩(각 1분 안쪽). 내레이션 없이 한국어 자막, 앱과 같은 그림체(말랑 스티커, Jua), 배경음은 앱의 종소리, 가로 16:9 mp4다.
- 영상은 README에 GitHub 첨부 영상으로 넣는다(`stardraft`의 README와 같은 방식).
- 영상의 스토리보드와 제작은 구현과 수동 통합 테스트가 끝난 뒤의 별도 작업이다. 완성된 앱 화면과 실제 경고 화면이 있어야 만들 수 있기 때문이다. README의 글 절차는 구현 때 쓰고 영상 자리는 나중에 채운다.

### 앱 내 업데이트

지도의 "자동 업데이트는 범위 밖"을 바꾼다. 사용자가 설정 화면에서의 업데이트와 재실행을 요청했다.

- 출처: electron-updater의 `github` 제공자로 공개 릴리스에서 직접 받는다.
- 확인: 앱이 시작할 때와 하루 한 번 저절로 확인한다. 인터넷이 안 되면 아무 표시 없이 넘어가고 설정 화면에서만 "새 버전을 확인할 수 없어요"와 "다시 확인"을 보여 준다.
- 내려받기: 새 버전을 찾으면 묻지 않고 미리 내려받아 검증까지 끝낸다. 검증에 실패한 파일은 버리고 아무것도 보여 주지 않는다.
- 표시: 검증이 끝나면 왼쪽 설정 단추에 주황 점을 붙이고, 설정 화면 맨 아래 "버전" 줄에 새 버전 번호와 "업데이트" 단추를 보여 준다. 새 버전이 없으면 지금 버전과 "최신이에요"만 있고 단추는 없다.
- 설치: "업데이트"를 누르면 확인 모달이 뜬다. 모달에는 강아지, "업데이트할까요?", 버전 변화, 무슨 일이 일어나는지 한 줄, 다음 종까지 남은 시간, "나중에" · "업데이트" 단추가 있다. 바뀐 내용 목록은 넣지 않는다. 승인해야만 설치하고 다시 실행한다. 저절로 설치하거나 다시 실행하는 일은 없다.
- 잠금: 다음 종까지 2분이 안 남았거나 종이 울리는 중이면 "업데이트" 단추를 잠그고 "종이 울린 뒤에 할 수 있어요"를 보여 준다.
- 끝난 뒤: 다시 실행되면 트레이에 숨은 상태가 아니라 창을 띄우고 위쪽에 "1.3.0으로 업데이트했어요" 알림을 잠깐 보여 준다.
- 두 OS의 화면과 흐름이 같다. Mac은 빌드 뒤 최상위 번들만 `designated => identifier "<앱 식별자>"`로 다시 서명해 Squirrel.Mac의 검증을 통과시킨다.
- 진위 확인: 업데이트 안내 파일에 Ed25519 서명을 넣고 앱에 넣은 공개 키로 검증한다. 개인 키는 개발 Mac의 Keychain에 두고 릴리스 명령이 거기서 읽는다. 사본은 `/Users/wraith/workspace/keys/ding-dong-dang`에 둔다(같은 Mac의 같은 디스크라는 점을 사용자에게 알렸다). 서명 필드는 처음부터 목록으로 둔다.
- 서명 방식과 검증을 고른 이유는 [ADR 0001](../../../docs/adr/0001-in-app-update-trust.md)에 있다.
- 새 버전마다 Windows SmartScreen 경고와 Mac의 "그래도 열기"를 다시 거치는 것은 사이트에서 새로 내려받아 설치할 때만 해당한다. 앱 내 업데이트는 그 경고를 거치지 않는다(`stardraft` 실기 확인 기준, 딩동댕에서는 구현 뒤 확인).

시안: [업데이트 화면 시안](../assets/11-update-flow.html) (전달 주소 `https://macbook-m5-pro.tail9db1f7.ts.net:8445/ding-dong-dang/update-flow.html`). 설정 화면의 다른 줄과 강아지 테마 그림은 자리만 잡은 것이다.

### 확인하지 못한 것

[구현 뒤 점검 목록](../checklists/post-implementation.md)으로 넘겼다.

- Windows 11에서 앱 내 업데이트가 끝까지 도는지, 앱이 받은 설치 파일에 SmartScreen이나 Smart App Control이 반응하는지.
- 딩동댕의 Electron 버전에서 Mac 앱 내 업데이트와 재실행이 되는지(`stardraft`는 Electron 44에서 확인했다).
- 실제 브라우저에서 다운로드 버튼을 눌렀을 때 페이지가 남고 내려받기만 시작되는지.
- 릴리스를 사전 릴리스로 바꾸면 고정 주소와 앱이 바로 이전 버전을 가리키는지.
