# 스펙: 의견 보내기 (제보 경로)

Status: ready-for-agent

근거는 2026-11-18~19 grilling 대화와 `docs/adr/0002-feedback-via-n8n-form.md`다. 용어는 루트 `GLOSSARY.md`(특히 **제보**), 화면의 색 · 글자 · 부품 · 문구는 루트 `DESIGN.md`를 따른다. 이 스펙과 `DESIGN.md`가 다르면 멈추고 사용자에게 확인한다.

## Problem Statement

딩동댕을 쓰는 학원 강사는 버그를 만나거나 불편한 점이 있어도 개발자에게 알릴 길이 없다. 앱에는 계정도 서버도 없고, 사용자는 PC와 개발 도구에 익숙하지 않아 GitHub 이슈 같은 경로를 쓸 수 없다. 개발자는 사용자가 겪는 문제를 모른 채 다음 버전을 만들게 되고, 제보가 와도 어느 버전 · 어느 OS에서 생긴 일인지 사용자에게 다시 물어야 한다.

개발자는 딩동댕 말고도 개인 제품(meka-base-jeju 등)을 운영한다. 제품마다 제보 경로를 따로 만들면 관리할 곳이 제품 수만큼 늘어난다. 나중에는 모인 제보를 LLM이 먼저 읽고 분석 초안을 만들게 하고 싶어서, 제보가 처리 상태와 함께 한곳에 쌓여야 한다.

## Solution

설정 화면의 버전 줄 아래에 "의견 보내기" 줄이 생긴다. "보내기"를 누르면 기본 브라우저에서 개발자가 호스팅하는 n8n 폼 페이지("딩동댕에 의견 보내기")가 열린다. 사용자는 종류(버그 / 개선 제안)를 고르고 내용을 쓴 뒤, 원하면 답장 받을 이메일과 스크린숏 한 장을 붙여 보낸다. 앱 버전과 OS는 앱이 주소에 담아 넘기므로 사용자는 적지 않는다.

제출된 제보는 n8n의 Data Table에 한 줄로 쌓이고, 개발자 Gmail로 알림 메일이 온다. 연락처가 있으면 메일에서 바로 답장할 수 있다. 같은 n8n 흐름은 제품마다 폼 하나를 더해 다른 제품도 쓸 수 있다.

## User Stories

진입과 열기

1. 학원 강사로서, 설정 화면에서 "의견 보내기" 줄을 찾고 싶다. 앱 정보(버전) 옆에서 자연스럽게 발견하기 위해서다.
2. 학원 강사로서, "의견 보내기" 줄에 버그와 불편한 점을 보낼 수 있다는 짧은 설명을 보고 싶다. 불편 사항도 보내도 되는지 망설이지 않기 위해서다.
3. 학원 강사로서, "보내기"를 누르면 브라우저에서 폼이 바로 열리길 바란다. 주소를 직접 입력하지 않기 위해서다.
4. 학원 강사로서, 키보드만으로 "보내기"에 초점을 옮기고 누를 수 있길 바란다. 마우스 없이도 쓸 수 있게 하기 위해서다.
5. 화면 읽기 프로그램 사용자로서, "보내기" 단추가 무엇을 보내는지 담은 이름으로 읽히길 바란다. 다른 "보내기"와 헷갈리지 않기 위해서다.
6. 학원 강사로서, 단추가 브라우저를 연다는 것을 아이콘으로 알 수 있길 바란다. 앱 밖으로 나가는 것에 놀라지 않기 위해서다.
7. 학원 강사로서, 폼을 열어도 딩동댕이 그대로 켜져 있고 종이 계속 울리길 바란다. 제보하는 동안 수업 종을 놓치지 않기 위해서다.

폼 쓰기

8. 학원 강사로서, 폼 제목에서 "딩동댕"을 보고 싶다. 제대로 된 곳에 왔는지 확인하기 위해서다.
9. 학원 강사로서, 종류를 버그와 개선 제안 중에서 고르고 싶다. 개발자가 급한 것부터 볼 수 있게 하기 위해서다.
10. 학원 강사로서, 내용을 여러 줄로 자유롭게 쓰고 싶다. 상황을 내 말로 설명하기 위해서다.
11. 학원 강사로서, 내용을 비운 채로는 보내지지 않길 바란다. 실수로 빈 제보를 보내지 않기 위해서다.
12. 학원 강사로서, 답장이 필요할 때만 이메일을 적고 싶다. 연락처를 꼭 남기지 않아도 되게 하기 위해서다.
13. 학원 강사로서, 화면 스크린숏을 한 장 붙이고 싶다. 글로 설명하기 어려운 문제를 보여 주기 위해서다.
14. 학원 강사로서, 앱 버전과 OS를 직접 적지 않아도 되길 바란다. 그런 정보를 어디서 찾는지 몰라도 되게 하기 위해서다.
15. 학원 강사로서, 폼 설명에서 앱 버전과 OS도 함께 간다는 사실을 보고 싶다. 무엇이 보내지는지 알고 보내기 위해서다.
16. 학원 강사로서, 보낸 뒤 접수됐다는 문장을 보고 싶다. 제대로 보내졌는지 알기 위해서다.

개발자가 받기

17. 개발자로서, 제보가 올 때마다 Gmail로 알림을 받고 싶다. 따로 확인하러 가지 않기 위해서다.
18. 개발자로서, 메일 제목에서 제품과 종류와 내용 첫머리를 보고 싶다. 받은편지함에서 바로 급한 것을 가리기 위해서다.
19. 개발자로서, 메일 본문에서 종류 · 내용 · 연락처 · 버전 · OS · 받은 시각 · 표의 행 번호를 보고 싶다. 표를 열지 않고도 상황을 파악하기 위해서다.
20. 개발자로서, 스크린숏을 메일 첨부로 받고 싶다. 사용자가 본 화면을 그대로 보기 위해서다.
21. 개발자로서, 연락처가 있는 제보는 메일에서 "답장"만 눌러 사용자에게 답하고 싶다. 주소를 옮겨 적지 않기 위해서다.
22. 개발자로서, 모든 제보가 n8n Data Table에 한 줄씩 남길 바란다. 메일을 지워도 기록이 남게 하기 위해서다.
23. 개발자로서, 각 제보에 처리 상태("새 제보" / "닫힘")가 있길 바란다. 처리한 것과 안 한 것을 구분하기 위해서다.
24. 개발자로서, 다 본 제보를 n8n 표 화면에서 "닫힘"으로 바꾸고 싶다. 별도 도구 없이 정리하기 위해서다.
25. 개발자로서, 어떤 제보가 어느 버전 · 어느 OS에서 왔는지 알고 싶다. 사용자에게 다시 묻지 않고 재현하기 위해서다.
26. 개발자로서, 제품 이름이 주소 쿼리가 아니라 들어온 폼으로 정해지길 바란다. 주소를 고친 제출이 다른 제품으로 섞이지 않게 하기 위해서다.
27. 개발자로서, 링크 미리보기 봇과 크롤러가 폼을 제출하지 못하길 바란다. 쓸모없는 줄이 쌓이지 않게 하기 위해서다.

여러 제품

28. 개발자로서, 다른 제품을 붙일 때 Form Trigger 하나만 복사해 제목과 설명만 바꾸고 싶다. 저장과 알림을 다시 만들지 않기 위해서다.
29. 개발자로서, 제품마다 폼 경로가 `/form/<저장소 이름>` 규칙을 따르길 바란다. 경로를 보고 제품을 알기 위해서다.
30. 개발자로서, 경로와 쿼리 이름 규칙이 n8n 워크플로 안에 적혀 있길 바란다. 새 제품을 붙일 때 한곳만 보면 되게 하기 위해서다.
31. 다른 제품의 개발자로서, `version`과 `os`를 채워 폼 주소를 여는 것만 하면 되길 바란다. 각 제품이 자기 정보를 책임지되 화면은 만들지 않기 위해서다.
32. 개발자로서, 나중에 LLM 분석 도구가 처리 상태를 보고 아직 안 본 제보를 꺼낼 수 있는 구조이길 바란다. 분석 자동화를 붙일 때 저장 방식을 바꾸지 않기 위해서다.

알림과 신뢰

33. 학원 강사로서, README에서 의견 보내기로 무엇이 어디로 가는지 읽고 싶다. 개인 서버로 무엇이 가는지 알고 쓰기 위해서다.
34. 학원 강사로서, 시간표나 종소리 같은 앱 데이터는 보내지지 않는다는 것을 알고 싶다. 안심하고 쓰기 위해서다.
35. 개발자로서, 앱이 설정 화면을 열 때마다 개인 서버에 요청을 보내지 않길 바란다. 사용자가 보내려 할 때만 서버와 닿게 하기 위해서다.
36. 학원 강사로서, 서버가 꺼져 있으면 브라우저의 연결 오류를 보더라도 앱은 그대로 동작하길 바란다. 제보 경로 문제로 종이 영향을 받지 않기 위해서다.

## Implementation Decisions

결정의 이유와 버린 대안은 `docs/adr/0002-feedback-via-n8n-form.md`에 있다.

**n8n 워크플로 (개발자 n8n 인스턴스, MCP로 만든다)**

- 워크플로 하나에 제품별 Form Trigger(지금은 딩동댕 하나, 경로 `ding-dong-dang`)를 두고, 모두 같은 저장 · 알림 단계로 이어진다. 각 Form Trigger 바로 뒤에서 제품 이름을 그 폼의 상수로 붙인다.
- Form Trigger(v2.5) 설정: 제목 "딩동댕에 의견 보내기", 설명에 버그나 불편한 점을 알려 달라는 문장과 "앱 버전과 OS도 함께 보내요". n8n 기본 모양을 쓰고 customCss는 넣지 않는다. n8n 표시(attribution)는 끈다. `ignoreBots`를 켠다. 인증은 없다. 단추 문구는 "보내기", 제출 뒤 문장은 접수됐다는 "~해요"체 문장이다.
- 폼 항목: 종류(라디오, "버그" / "개선 제안", 필수), 내용(여러 줄, 필수), 답장 받을 이메일(이메일, 선택), 스크린숏(파일, 이미지 1장, 선택), 숨김 필드 `version`과 `os`(쿼리로 받는다).
- Data Table 하나에 제보를 쌓는다. 칸: 제품, 종류, 내용, 연락처, 버전, OS, 첨부 있음(참/거짓), 받은 시각, 상태. 행 id는 Data Table이 만든다. 상태는 "새 제보"로 시작하고 값은 "새 제보"와 "닫힘" 둘뿐이다. 파일은 표에 넣지 않는다.
- 알림은 Send Email(SMTP) 노드로 보낸다. 자격 증명은 사용자가 Gmail 앱 비밀번호로 직접 등록한다. 받는 주소는 보내는 계정과 같은 개발자 Gmail. 제목은 `[<제품 표시 이름>][<종류>] <내용 첫 줄 40자>`. 본문은 종류 · 내용 · 연락처 · 버전 · OS · 받은 시각 · 표의 행 번호. 스크린숏이 있으면 첨부한다. 연락처가 있으면 Reply-To를 그 주소로 둔다.
- 워크플로 설명과 스티키 노트에 공용 규칙을 적는다: 경로는 `/form/<저장소 이름>`, 쿼리는 `version`(제품 버전)과 `os`(사람이 읽는 OS 이름과 버전), 값을 채우는 책임은 각 제품, 제품 이름은 폼으로 정한다. 이것이 규칙의 원본이다.

**딩동댕 메인 프로세스**

- 제보 폼 주소를 만드는 순수 함수 하나를 둔다. 입력은 앱 버전, 플랫폼, 시스템 버전이고 출력은 완성된 주소다. n8n 호스트와 경로 `ding-dong-dang`은 상수다. 쿼리 값은 URL 인코딩한다.
- `os` 값: macOS는 `macOS <시스템 버전>`, Windows는 `Windows <시스템 버전>`. 시스템 버전은 Electron의 `process.getSystemVersion()`, 앱 버전은 `app.getVersion()`에서 얻는다.
- 렌더러 → 메인 명령에 "의견 보내기 폼 열기"를 하나 더한다. 기존 "자동 시작 등록 방법 열기" 명령과 같은 모양(인자 없음)이고, 메인은 위 함수로 만든 주소를 `shell.openExternal`로 연다. 열기 전에 서버 상태를 확인하지 않고, 열기 실패도 따로 알리지 않는다.
- 설정 화면을 열거나 앱을 띄울 때 n8n으로 요청을 보내지 않는다.

**딩동댕 설정 화면**

- 버전 줄 바로 아래, "모든 데이터" 줄 바로 위에 "의견 보내기" 줄을 둔다. 줄 이름 "의견 보내기", 보조 글자로 짧은 설명(예: "버그나 불편한 점"), 오른쪽에 작은 옅은 단추 "보내기"와 바깥으로 나가는 화살표 SVG 아이콘.
- 단추의 화면 읽기 이름은 대상을 담는다(예: "의견 보내기 폼 열기"). 모양 · 초점 · 문구는 `DESIGN.md`의 단추와 글 규칙을 따른다. 새 색이나 새 부품은 쓰지 않는다.
- 세로 줄 단추와 트레이 · 메뉴 막대 메뉴에는 넣지 않는다.

**문서**

- `DESIGN.md`의 설정 화면 항목 순서에 "의견 보내기"를 버전과 모든 데이터 사이에 더한다.
- README에 "의견 보내기" 절을 더한다: 설정 화면에서 여는 법, 보내는 것(쓴 내용, 선택한 이메일과 스크린숏, 앱 버전과 OS), 개발자만 본다는 것, 시간표 · 종소리 등 앱 데이터는 보내지 않는다는 것. 말투는 README의 "~해요"체.

## Testing Decisions

좋은 테스트는 겉으로 드러나는 동작만 확인한다: 화면에 무엇이 어디 보이는지, 누르면 어떤 주소가 열리는지, 함수가 어떤 주소를 돌려주는지. 명령 이름이나 내부 호출 순서는 확인하지 않는다.

- **주 이음새: Playwright Electron e2e.** 설정 화면에서 "의견 보내기" 줄의 단추를 누르면 메인이 여는 주소를 확인한다. `electronApp.evaluate`로 메인의 `shell.openExternal`을 가로채 받은 주소를 기록한다. 경로가 `/form/ding-dong-dang`이고, `version`이 앱 버전과 같고, `os`가 비어 있지 않은지 본다. 키보드로 초점을 옮겨 누르는 경우도 포함한다. 기존 설정 화면과 자동 시작 e2e(`--data-dir` 실행, 헤드리스 실행 포함)가 선례다.
- **보조: 주소 함수 단위 테스트(vitest).** e2e는 개발 Mac에서만 돌기 때문에 Windows 값은 여기서만 확인한다. macOS · Windows 각각의 `os` 값, 공백 등 인코딩이 필요한 값, 경로와 호스트가 상수대로인지 본다. 메인 쪽 순수 함수 테스트(업데이트 서명, 스케줄러 등)가 선례다.
- **기존 이음새 재사용.** 설정 화면 렌더 테스트에 "의견 보내기" 줄이 버전 줄 다음, "모든 데이터" 줄 앞에 있고 단추가 대상을 담은 이름으로 읽히는지 더한다(지금 "버전 줄이 '모든 데이터' 바로 위"를 확인하는 테스트를 새 순서에 맞게 고친다). README 링크 테스트의 "요구된 절" 목록에 "의견 보내기"를 더한다. 디자인 토큰 · 대비 테스트는 새 CSS가 토큰만 쓰는지 그대로 잡는다.
- **n8n 워크플로.** 앱 테스트로 확인하지 않는다. 테스트 제출 한 번으로 Data Table에 한 줄이 생기고(상태 "새 제보", 제품 "딩동댕", 버전 · OS가 쿼리 값대로) Send Email 노드가 성공하는지 n8n 실행 기록으로 확인한다. 쿼리로 다른 `product`를 넣어도 제품 칸이 바뀌지 않는지도 같은 방법으로 본다.
- 완료 전 `npm run check`(타입 검사, 린트, 단위 테스트, e2e)가 통과해야 한다. 실제 받은편지함 도착과 Windows 실기 동작은 구현이 모두 끝난 뒤 사용자의 수동 통합 테스트로 확인한다.

## Further Notes

- 사용자 개입은 하나다: Gmail 2단계 인증 계정에서 앱 비밀번호를 만들어 n8n에 SMTP 자격 증명으로 직접 등록한다. 비밀번호는 에이전트를 거치지 않는다. n8n 워크플로 작업은 이 등록 뒤에 할 수 있다. n8n의 공개 호스트 주소는 에이전트가 기존 워크플로와 인스턴스 설정에서 찾고, 찾지 못하면 같은 사용자 개입 티켓에서 묻는다.
- 폼 주소는 배포된 앱마다 들어가므로 첫 릴리스 뒤에는 호스트와 경로를 바꾸지 않는다(ADR 0002의 Consequences).
- stardraft는 `~/workspace/work/` 아래의 업무용 도구다. 개인 제품의 제보를 그 도구에 넣어도 되는지는 연동을 grilling할 때 확인한다.
- n8n Data Table은 인스턴스 전체 용량 제한이 있다(기본값을 구현 때 확인). 텍스트 제보만 쌓으므로 v1에서는 문제가 되지 않을 것으로 본다.
